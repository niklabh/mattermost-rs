# Plugin host plan — Go plugins and Rust plugins on mm-rs

Written 2026-09-17. This is a plan, not a ledger: once a phase starts, its findings go in the code
and its status goes in `MIGRATION.md` (see CLAUDE.md, *Write the finding once*).

## 1. Why this is next

- **20 of the 25 api4 route+method pairs still unserved are plugin routes.** They are
  `api4/plugin.go` (2 of 12 served) and `api4/plugin_local.go` (0 of 10), per
  `scripts/routes.py` on 2026-09-17 against `27d4b58`. Behind them sit the `/plugins/{id}/*`
  handler (`app/channels.go:240-242`), 35 `RunMultiHook` call sites in `channels/app`, and three
  debt entries that name "no plugin host" as their cause: D-402, D-471 and D-542.
- The host is on the full denominator in CLAUDE.md. None of it is private code: `server/public/plugin`
  (Apache-2.0) and `channels/app/plugin*.go` (AGPL) are both in the tree. **So the host gets ported,
  not forwarded.**
- The old decision, "keep the Go plugin host alive indefinitely" (`MIGRATION_STRATEGY.md` §5,
  `MIGRATION.md` *Out of scope*), predates the 2026-09-15 end state and no longer holds.

## 2. What Go actually does (checked against the pinned tree)

The protocol is narrower than "hashicorp go-plugin", and it shapes every decision below.

| Fact | Where |
|---|---|
| Mattermost uses go-plugin's **net/rpc** protocol, not gRPC. "gRPC is not supported." | `public/plugin/client.go:57` |
| go-plugin **v1.8.0**, yamux **v0.1.2** | `server/go.mod:150,154` |
| Handshake: `ProtocolVersion 1`, cookie `MATTERMOST_PLUGIN` = `Securely message teams, anywhere.` | `public/plugin/api.go:1779` |
| Host sets `MATTERMOST_PLUGIN`, `PLUGIN_MIN_PORT`, `PLUGIN_MAX_PORT` and `PLUGIN_PROTOCOL_VERSIONS` (plus the unix socket dir/group) in the child's environment. The child prints `CORE\|APP\|network\|addr\|protocol\|servercert` on stdout. | go-plugin `client.go:639-717`, `server.go:425-445` |
| `SecureConfig` = SHA-256 of the executable. No AutoMTLS. `StartTimeout` 3s. | `supervisor.go:45-78,124` |
| The connection is **yamux**. Stream 1 is control (net/rpc services `Control.Ping`, `Control.Quit`, `Dispenser.Dispense`), streams 2 and 3 carry stdout and stderr. Further streams go through **MuxBroker**: ids come from a counter, and the acceptor acks each one by writing the u32 id little-endian. | go-plugin `rpc_client.go:65-100`, `rpc_server.go:66-117`, `mux_broker.go` |
| Every payload is **encoding/gob** over net/rpc. Args and returns are generated `Z_<Name>Args`/`Z_<Name>Returns` structs with fields `A`, `B`, `C` and so on. | `client_rpc_generated.go` (9,600 lines, generated by `interface_generator/main.go`) |
| **52 hooks, 258 API methods.** 20 of them are hand-written because generation cannot express them: ServeHTTP, PluginHTTP, MessageWillBePosted (decode-into-original), LogAuditRec (gob-safe maps), UploadData, and others. | `hooks.go`, `api.go`, `interface_generator/main.go:25` |
| `OnActivate` opens two reverse brokered streams: an **API server** and a **database/sql driver server** (`dbRPCServer`). Plugins run arbitrary SQL through the host's pool. | `client_rpc.go:271-352`, `db_rpc.go`, `app/plugin_db_driver.go` |
| ServeHTTP streams the response writer as a nested net/rpc server on a brokered stream. The request body uses a varint-length pull protocol, and websocket upgrades use `Hijack` RPCs. | `client_rpc.go:432-540`, `io_rpc.go`, `hijack.go` |
| Errors cross the wire as registered gob interface values: `*model.AppError`, `*pq.Error`, or `*ErrorString{Code,Err}`, where codes 1-7 map back to `io.EOF`, `sql.ErrNoRows` and so on. | `client_rpc.go:146-231` |
| Gob interface registrations include a **legacy name**: `[]*model.SlackAttachment`. | `client_rpc.go:219` |

Two consequences are easy to miss, and a wrong guess on either breaks every plugin:

1. **Gob matches struct fields by Go field name, not by JSON tag.** `mm-model` renames every field
   to its JSON name, so its serde derives cannot be reused for gob. Worse, 41 model fields are
   tagged `json:"-"` and gob still carries them. `Post.Filenames` (`post.go:159`) and
   `ChannelMember.NotifyProps` (`channel_member.go:38`) are two examples, and a JSON-shaped Rust
   struct may simply not have them.
2. **Gob decodes into an existing value and omits zero fields.** A field left out of the message
   keeps the destination's old value. Go relies on this deliberately for `MessageWillBePosted`, so
   that "older plugins" do not strip new fields (`client_rpc.go:878`). A decoder that builds a
   fresh value is wrong on that hook.

## 3. Decisions

### D1 · One wire protocol for every out-of-process plugin: go-plugin net/rpc + gob

The Rust host speaks exactly what the Go host speaks. A Rust plugin SDK speaks exactly what a Go
plugin speaks. That buys three things no other design does:

- **Existing Go plugin binaries run unmodified**, marketplace bundles included.
- **A Rust plugin built on the SDK also runs on stock Go Mattermost.** Plugin authors lose nothing
  by choosing Rust, and the SDK can be tested against the real Go host we already run on the stack.
- **The parity oracle is symmetric.** Go host ↔ Rust plugin and Rust host ↔ Go plugin are both
  testable, so every layer gets a Go counterpart to diff against.

### D2 · WebAssembly: good for a later, optional Rust-only runtime; wrong as the foundation

| Question | Answer |
|---|---|
| Can existing Go plugins run as Wasm? | **No.** They ship as native binaries per OS/arch (`manifest.go:227`, `Executables`). The SDK imports go-plugin, net/rpc and `lib/pq`. `GOOS=wasip1` has no sockets. Recompiling the ecosystem is not in our control. |
| Can Wasm replace the RPC protocol for Rust plugins? | Technically, yes: wasmtime with the component model and a WIT world generated from the same IDL (D5). |
| What would it buy? | In-process calls (no gob, no per-hook syscall round trip), a memory and fuel sandbox, one portable artifact instead of per-platform executables, and no child-process supervision. |
| What would it cost? | The plugin would **not** run on Go Mattermost. The `Driver` API hands out raw SQL connections, so it would need a host-mediated rewrite. Background work, timers and outbound HTTP depend on WASI async and `wasi:http` maturity. ServeHTTP streaming and hijacked websockets need resource-typed streams. And the result is a second API surface of 258 methods to keep in step. |
| Verdict | **Phase 9, behind a `PluginRuntime` trait, decided after the native path is proven.** The trait is designed in Phase 4 so that Wasm slots in without reshaping the environment. Don't build it first: it serves no existing plugin and closes none of the 20 routes. |

In-process `dylib` Rust plugins are **rejected**. Rust has no stable ABI, there is no isolation,
and a plugin panic or `abort` takes down the server, which is exactly what Go's process
boundary exists to prevent.

### D3 · Crate split: three generic crates, one Mattermost crate, the host in mm-app

```
  generic, publishable, no mm-* dependency           Mattermost-specific
  ───────────────────────────────────────           ─────────────────────────────────────
  gobwire           Go encoding/gob codec            mm-plugin      (Apache-2.0, from server/public)
    └ gobwire-derive  #[derive(Gob)]                   ├ generated Z_*Args/Returns, hook ids
  go-netrpc         Go net/rpc client+server           ├ gob adapters for mm-model types
    └ gobwire                                          ├ feature "host": hooks client, API/Driver
  goplugin          go-plugin protocol, both sides     │   server traits, ServeHTTP streaming
    ├ yamux, go-netrpc                                 └ feature "sdk":  hooks server, API client
    └ feature "grpc" (tonic) — Phase 8                    = the Rust plugin SDK
                                                      mm-app::plugin  (AGPL, from channels/app)
                                                        Environment, supervisor, RunMultiHook,
                                                        PluginAPI impl, DB driver, bundles
```

- **Names.** `gob` is taken on crates.io by an unmaintained 0.1.0 from 2018. `gobwire`,
  `go-netrpc` and `goplugin` were free on 2026-09-17. Keep "hashicorp" out of every crate name,
  because it is their trademark.
- **Licences.** `gobwire` and `go-netrpc` are original implementations of documented Go formats,
  so use `MIT OR Apache-2.0`. `goplugin` reimplements an MPL-2.0 library's protocol, so match it
  with MPL-2.0. That removes the question at no cost to users, because MPL is file-level.
  `mm-plugin` is Apache-2.0 like `mm-model`, and the environment in `mm-app` stays AGPL. Accepted
  by the maintainer on 2026-09-17 (see §7).
- **Boundary enforcement.** A test runs `cargo tree -p <generic crate>` and fails on any `mm-`
  dependency. The generic crates get their own README, CHANGELOG and docs.rs-clean docs from the
  start, not at publish time.

### D4 · `gobwire` has its own derive, not serde

Serde's data model has no gob *interface value* (a registered type name plus a nested typed value),
no decode-into-existing merge, and it would force JSON renames and gob names onto one struct. So:

- `trait GobEncode` / `trait GobDecode { fn decode_into(&mut self, …) }`, with merge semantics as
  the primitive and "decode fresh" as `Default` plus merge.
- `#[derive(Gob)]` with `#[gob(name = "Id")]`, plus a `TypeRegistry` for interface values that
  supports `RegisterName` aliases.
- **The encoder and decoder are stateful per stream.** Gob sends each type definition once per
  connection, so net/rpc must own one encoder and one decoder for each direction.
- Covered: unsigned and signed varints, byte-reversed floats, complex numbers, strings, bytes,
  slices, arrays, maps, nested and recursive structs, field deltas, zero omission, pointer
  flattening, and `GobEncoder`, `BinaryMarshaler` and `TextMarshaler` types. `time.Time` gets its
  versioned binary form with the zone offset.
- A `gobwire::Value` dynamic type for `map[string]any`/`[]any`, the gob analogue of the
  `serde_json::Value` rule in CLAUDE.md.
- Optional `serde` feature later, for users who only need plain structs.

### D5 · Generate the Mattermost surface from Go; never hand-transcribe it

`reference/dump/plugingen/` is a Go program that loads `public/plugin` with `go/types` and emits
`fixtures/plugin_idl.json`. For every hook and API method, the IDL records the name, the hook id,
parameter and return Go types, the `Z_` struct names and field letters, and whether the method is
in the hand-written set. For every model type reachable from those signatures, it records **every
field**: Go name, Go type, JSON tag, `json:"-"`-ness and exported-ness. Then
`scripts/plugingen.py` turns that IDL into committed Rust under `mm-plugin/src/generated/`:

- `Z_*` wire structs, `HookId`, and `const HOOK_NAMES`
- `impl GobEncode/GobDecode for mm_model::X`, mapping Go field names to Rust fields. **The
  generator fails** when a Go field has no Rust counterpart, so the 41 `json:"-"` fields surface
  as a list at generation time instead of as silent drops at runtime.
- The `Hooks` trait, the `PluginApi` trait (258 methods, each defaulting to a typed
  "not implemented" `AppError`) and the `Driver` trait
- Later, the WIT world for D2's Wasm runtime, from the same IDL

A drift check (`plugingen --check`) runs in the test suite, so a new API method in the reference
tree fails loudly.

### D6 · Coexistence: exactly one process hosts plugins at a time

Mattermost HA already runs one copy of every plugin per node, and plugins coordinate through KV
mutexes in the shared database. But two hosts here would behave like two HA nodes **without a
cluster bus**. `PublishPluginClusterEvent` would go nowhere, a plugin's `PublishWebSocketEvent`
would reach only its own host's hub, and `OnConfigurationChange` would fire on one side only. So:

- A single switch, `MMRS_PLUGIN_HOST=go|rust`, defaulting to `go` until Phase 5 exit.
- When `rust`: mm-api serves `/plugins/*`, `/static/plugins/*` and the plugin api4 routes itself,
  and the Go process is started with plugins off. **To verify in Phase 4**: whether Go's
  `MM_PLUGINSETTINGS_ENABLE=false` environment override disables its environment without writing
  to the shared config.
- Whichever process is not the host fires no hooks. That is today's D-402 with the sides swapped,
  and each hook call site still unported to Rust is a debt entry with that shape. The flip to
  `rust` is justified by measurement: the number of hook call sites on write paths each side
  serves.

## 4. Phases

Each phase has an exit test. Mutation testing (CLAUDE.md) applies from Phase 1 on. The route-sized
units in Phases 4-6 keep rule 1: each ports one handler plus what it needs.

### Phase 0 · Spikes that can kill the design (1 session)

Every spike below prints its result into the session report. Any "no" reshapes D3 before real
code is written.

1. **yamux interop.** Run the Rust `yamux` crate (0.14, libp2p) against `hashicorp/yamux` v0.1.2
   in both directions, with 300 concurrent streams (a busy ServeHTTP opens two per request), 64 MB
   transfers, and 35 s idle to cross hashicorp's keepalive. If backlog limits or window semantics
   diverge, the fallback is our own yamux module in `goplugin`. The spec is short, so that is
   roughly 1,200 lines.
2. **Gob decode of real traffic.** Build a Go program that gob-encodes a `Z_ServeHTTPArgs` and a
   `Z_MessageWillBePostedArgs`, then hand-decode them in a throwaway Rust test. The goal is to
   size `gobwire` honestly.
3. **Launch a real plugin.** A 40-line Go plugin in `reference/dump/plugins/hello/` goes through a
   throwaway Rust launcher: handshake, `Dispenser.Dispense("hooks")`, `Plugin.Implemented`,
   `Control.Quit`.

### Phase 1 · `gobwire` (+ derive)

- The oracle is `reference/dump/gob/`, and it is **bidirectional**. `gen` writes `fixtures/gob/*.gob`
  from fully populated values: every kind, every zero-omission edge, interfaces, recursion, merge
  cases, and time zones. `echo` reads gob on stdin, decodes it into a named Go type and re-encodes
  it. This is how Rust→Go is proven: Go must *accept* what Rust wrote, and byte equality is not
  expected, because Go map order is random.
- The tests are value-graph equality for Go→Rust, `echo` round trips for Rust→Go, and a
  `cargo fuzz` target whose crashes are replayed through `echo`.
- **Exit:** every fixture decodes; every Rust encoding is accepted by `echo`; the merge-decode
  corpus matches Go's resulting values field by field.

### Phase 2 · `go-netrpc` + `goplugin` (net/rpc protocol, both sides)

- `go-netrpc`: `Request{ServiceMethod, Seq}` and `Response{ServiceMethod, Seq, Error}`, a
  concurrent client multiplexed by `Seq`, and a server dispatching `"Service.Method"` to async
  handlers. Go's `ServerError` string semantics are kept exactly.
- `goplugin` host: `ClientConfig` (cmd, handshake, plugin set, `SecureConfig` checksum, start
  timeout, min/max port, unix socket dir), launch, stdout line parse, reattach
  (`model.PluginReattachConfig`), stdio stream sync, forwarding of go-hclog JSON log lines to
  `tracing` at the right level, `Dispense`, `Ping`, `Kill` (Quit, then grace period, then SIGKILL).
  `MuxBroker` gets `next_id`, `accept(id)` with Go's 5 s timeout, and `dial(id)`.
- `goplugin` plugin side: `serve(ServeConfig)`, the magic-cookie check, the protocol-version
  negotiation, the listener (unix socket or TCP within the port range), the protocol line, stdio
  pipes, and signal handling.
- The oracle is the interop matrix, run in CI against go-plugin@v1.8.0's own net/rpc example
  (`examples/basic`) and the Phase 0 hello plugin:

  | host \ plugin | Go | Rust |
  |---|---|---|
  | Go | (reference) | must pass |
  | Rust | must pass | must pass |
- **Exit:** the whole matrix is green, including kill during an in-flight call, a plugin crashing
  mid-stream, a checksum mismatch, a wrong cookie, and reattach.

### Phase 3 · `mm-plugin`: the Mattermost wire surface, both directions

- The D5 generator and its output. Hand-written ports of the 20 excluded methods, with
  ServeHTTP/PluginHTTP streaming, `io_rpc` varint pull, the hijack RPCs, and the `LogAuditRec`
  gob-safe conversion. Error encoding covers `ErrorString` codes, `AppError` and `pq.Error`.
- `feature = "host"`: `HooksClient` (holds `implemented[]`, skips unimplemented hooks exactly as
  `client_rpc_generated.go:191` does, and has the `WithRPCErr` variants) and the API and Driver
  servers over the traits.
- `feature = "sdk"`: `mm_plugin::client_main(impl Hooks)`, `Implemented` computed from the trait
  impl, and an async `PluginApi` client. **This is the Rust plugin SDK.**
- The oracle is `reference/dump/plugins/conformance/`, a Go plugin that implements every hook
  with deterministic answers derived from its inputs and, on `OnActivate`, runs a scripted tour of
  the API against a recording fake. It writes a transcript. Run it under a stub Go host and a stub
  Rust host and diff the transcripts. Then run a Rust conformance plugin (SDK) under the **real Go
  server** on the stack.
- **Exit:** both transcripts are equal, and the Rust conformance plugin activates, serves HTTP and
  answers `MessageWillBePosted` on real Go Mattermost.

### Phase 4 · The environment in `mm-app` and the plugin routes

This is route-sized work from here on, so the ledger counts it.

- Port `public/plugin/environment.go`, `supervisor.go`, `health_check.go` and
  `hooks_timer_layer` (metrics), plus `app/plugin.go`, `plugin_install.go`,
  `plugin_signature.go`, `plugin_public_keys.go`, `plugin_statuses.go`,
  `plugin_db_driver.go` (the Driver, with sqlx and dynamic binds producing gob `driver.Value`s)
  and `plugin_requests.go`.
- Introduce `trait PluginRuntime`, with `Process` as its only implementation, so D2 has a seam.
- Serve in this order: `GET /plugins/statuses`, `GET /plugins`, `GET /plugins/webapp`,
  enable/disable, `POST /plugins` (upload), remove, install_from_url, marketplace; then the 10
  local-mode routes, including reattach/detach. Then `/plugins/{id}/*` and `/static/plugins`.
- Settle D6's Go-side switch.
- **Exit:** all 22 plugin route pairs served with parity suites. The stack gains a real plugin
  installed on both sides, not an empty `plugins/` directory.

### Phase 5 · Hook call sites

Wire the 35 `RunMultiHook` sites into the Rust write paths already served, ordered by client
traffic. This closes D-402, D-471 and D-542. Each site's parity test runs the conformance plugin
under `MMRS_PLUGIN_HOST=go` and then `=rust`, and diffs what the plugin observed. **Exit:** every
hook site on a Rust-served write path fires, and D6's switch defaults to `rust`.

### Phase 6 · The 258 API methods

These are ordered by real use: `scripts/plugin-api-usage.py` counts `p.API.*` and `pluginapi`
calls across the widely installed open-source plugins (Playbooks, Calls, Jira, GitHub, GitLab,
Zoom, AI, Boards). Most methods are thin wrappers over app functions that routes already ported.
Unported ones return the typed not-implemented `AppError` and are counted, never silently
succeeding. **Exit:** those plugins' own e2e flows pass under the Rust host.

### Phase 7 · Publish

`gobwire`, `gobwire-derive`, `go-netrpc` and `goplugin` go to crates.io. They need a docs pass,
examples (a Rust host driving a Go plugin, and a Rust plugin for a Go host), MSRV CI and semver
checks. `mm-plugin`'s SDK is published as a separate crate once Phase 3's Go-server test has
stayed green for a release.

### Phase 8 · gRPC in `goplugin` (generic value, not needed by Mattermost)

Add `GRPCBroker`, `GRPCStdio`, `GRPCController`, the `plugin` health service, AutoMTLS (rustls and
rcgen) and gRPC broker multiplexing (the seventh protocol-line segment). Most HashiCorp-ecosystem
plugins (Terraform, Vault, Packer) speak gRPC, so this is what makes the crate broadly useful.
Test it against go-plugin's `examples/grpc`.

### Phase 9 · Wasm runtime (decision point, not a commitment)

Re-evaluate against D2 with Phases 4-6 in hand. If it goes ahead: wasmtime component model, a WIT
world generated from the IDL, `PluginRuntime::Wasm`, and host-mediated DB access replacing
`Driver`.

## 5. Risks

| Risk | Mitigation |
|---|---|
| Rust `yamux` and hashicorp's differ under load | Phase 0 spike; own implementation as fallback |
| `mm-model` structs lack gob-only fields (`json:"-"`) | The D5 generator fails on the gap; add the fields where the types live, with their JSON skip |
| Gob merge-decode semantics mis-ported | Merge corpus in Phase 1; `MessageWillBePosted` gets its own conformance case |
| Go version drift in gob's `time.Time` or `x509` encodings (see `client_rpc.go:419`) | The oracle is built with the pinned Go; the IDL records the Go version |
| Plugins using `Driver` for arbitrary SQL against Postgres types sqlx doesn't bind dynamically | The Driver corpus in Phase 4 draws on the SQL real plugins send (Playbooks, Boards) |
| Scope creep into speculative API porting | Phase 6 is usage-ordered and each method is route-sized; unported methods are counted |
| Two hosts running at once | D6's single switch, and a startup check in mm-api that refuses `rust` while Go reports active plugins |

## 6. How progress is reported

The route count stays the headline (22 plugin route pairs out of 764). Beside it, report:
generated-surface coverage (hooks fired by Rust-served paths out of 35 call sites, API methods
implemented out of 258), the interop matrix state, and Driver methods out of the `db_rpc.go` set.
**Forwarded share: zero.** None of this is private code.
